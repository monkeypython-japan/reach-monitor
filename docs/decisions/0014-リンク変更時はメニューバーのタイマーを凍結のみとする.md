# ADR-0014: リンク変更時はメニューバーのタイマーを凍結のみとする

- ステータス: 承認 (Accepted)
- 日付: 2026-07-27

## コンテキスト

[[0012-メニューバーの経過時間表示をリンク接続かつ到達確認基準にする|ADR-0012]] により、
メニューバーの経過時間はリンクエッジ（`interfaceType` の変化）と到達性エッジの両方で
reset/freeze する仕様になった。このうちリンクエッジ側は「新しいリンクに繋がったら
即座に 0:00 にリセットする」という実装だった。

しかし実機（Starbucks の Wi-Fi、キャプティブポータル未ログイン）でこの不具合が観測された:
リンクが Wi-Fi (`at_STARBUCKS_Wi2`) に切り替わった直後、到達性が一度も確認されていない
（監視対象3件とも「不可」表示）にもかかわらず、メニューバーは黒丸（到達不可）+ `0:01` と、
経過時間タイマーが動き出してしまっていた。

原因は ADR-0012 のリンクエッジ実装がリンク接続時に無条件で `resetMenuBarTimer()` を呼んで
いたこと。到達性が一度も確認されないまま「healthy な時間」を示すタイマーが進んでしまい、
「メニューバーの経過時間 = リンク接続 かつ 到達確認、の両方が成立している時間」という
ADR-0012 自身の意図（"fully healthy"）と矛盾していた。

## 検討した選択肢

- **採用案**: リンクエッジ（`interfaceType` の変化）は新規接続・種別切替・リンク断のいずれの
  場合も無条件で `freezeMenuBarTimer()` のみを呼ぶ（リセットしない）。メニューバーのタイマーが
  0:00 から再スタートするのは、到達性エッジ（`apply(results:status:)` で `.reachable` が
  確認された瞬間）のみとする。つまり「リンクが変わった/切れた時点で必ず凍結し、その新しい
  リンクで到達性が確認できて初めて 0:00 から動き出す」という、ユーザーの意図通りの
  一方向的な流れになる。
- **却下案**: リンクエッジは維持しつつ、reset 前に一定の遅延（例: 到達確認1回分の
  猶予）を設ける — 却下理由: 複雑な割に、結局「その猶予中に到達確認が失敗したら結果的に
  凍結」という今回の採用案と同じ状態に帰着する。タイマーの意味を素直に「リンクとreachability
  が両方揃うまでは進まない」とする方が単純で分かりやすい。

## 決定

`AppState.linkMonitor.onUpdate` 内、`interfaceType` の変化を検知した際の処理を
`updateLinkTimer(newType:)`（新規接続で reset、リンク断で freeze）から、常に
`freezeMenuBarTimer()` のみを呼ぶ形に変更する。`updateLinkTimer(newType:)` は削除し、
呼び出し箇所は直接 `freezeMenuBarTimer()` を呼んでその場でログに渡す。

```swift
linkMonitor.onUpdate = { [weak self] info in
    Task { @MainActor in
        guard let self else { return }
        if info.interfaceType != self.link.interfaceType {
            self.freezeMenuBarTimer()
            self.linkHistory.logLinkChange(
                from: self.link, to: info, wifi: self.wifi,
                frozenElapsedSeconds: max(0, Int(self.menuBarTimerFrozenElapsed ?? 0))
            )
        }
        self.link = info
    }
}
```

`resetMenuBarTimer()` の呼び出し箇所は `apply(results:status:)` の到達性復旧パスのみになる
（変更なし）。`LinkHistoryLogger` は元々 `TimerEvent`（`.reset`/`.freeze`）を受け取っていたが、
リンクエッジは常に凍結のみになったため `.reset` ケースが到達不能コードになる。`TimerEvent`
enum を廃止し、`logLinkChange(...)` は凍結後の経過秒数（`frozenElapsedSeconds: Int`）を
直接受け取る形に簡略化した。

## 結果

### 利点

- リンク切替直後、到達性が確認されるまではメニューバーのタイマーが「凍結」表示のままになり、
  「まだ健全性が確認できていない」ことが一目で分かる。到達確認できて初めて 0:00 から動き出す
  ため、ADR-0012 の "fully healthy" という意図と実装が一致した。
- キャプティブポータル未ログインのような「リンクは繋がっているが到達性がない」状態を、
  メニューバーの経過時間だけで誤って「健全」と示さなくなった。
- `LinkHistoryLogger` 側の `TimerEvent` が単純化され、常に凍結イベントのみを記録する
  ようになった（不要になった `.reset` ケースを削除）。

### 欠点・トレードオフ

- 同一種別内での AP 切替（例: Wi-Fi から別 SSID の Wi-Fi へ、`interfaceType` が変化しない
  ローミング）は、今回の `interfaceType` ベースの検知では捉えられない。この Mac の実機
  ログでは観測された遷移がすべて `nil` を経由していた（AP 切替時に一度リンクが落ちてから
  再接続していた）ため実害は確認されていないが、`interfaceType` が変わらないまま SSID だけ
  変わるローミングが将来問題になった場合は、`WiFiInfo`（SSID/BSSID）の変化も検知対象に
  加える改修が必要になる。
