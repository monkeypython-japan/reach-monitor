# ADR-0015: 到達性が継続中のリンク変更後もメニューバーのタイマーをリセットする

- ステータス: 承認 (Accepted)
- 日付: 2026-07-27

## コンテキスト

[[0014-リンク変更時はメニューバーのタイマーを凍結のみとする|ADR-0014]] により、リンク変更は
メニューバーのタイマーを常に凍結のみ行い、到達性が確認された時点で 0:00 にリセットする
仕様にした。ところが実機（Ethernet、リンクの切断/変更なし、ポップオーバーの
「到達確認からの経過時間」は 03:32:03 と継続してカウントアップ中）で、メニューバーの
経過時間が「0:02」のまま更新されていない不具合が報告された。

原因は ADR-0014 の実装の見落とし: メニューバーのタイマーが 0:00 に戻る条件が
`apply(results:status:)` 内の `status == .reachable && previous != .reachable`
（＝到達性が非到達から到達へ**回復**した瞬間）のみだったこと。もしリンク変更が起きた
時点で到達性が**既にずっと `.reachable` のまま一度も途切れていなかった**場合、
`lastConfirmedStatus`（`previous` の元）は変更前後を通じて `.reachable` のまま
変わらないため、この「回復」条件は二度と成立しない。結果、リンク変更でいったん凍結された
メニューバーのタイマーは、その後どれだけ実際には健全な状態が続いても、永久にリセットされず
古い値のまま表示され続けてしまっていた。

## 検討した選択肢

- **採用案**: リンク変更によって凍結した直後は「新しいリンク上でまだ到達性が確認されて
  いない」ことを示すフラグ `menuBarAwaitingFreshReachability` を立てる。到達性判定
  （`apply(results:status:)`）側で、通常の「非到達から到達への回復」条件に加えて、
  「現在到達可能 **かつ** このフラグが立っている」場合もメニューバーのタイマーをリセット
  する条件に含める（フラグはリセット時にクリアする）。ポップオーバー用の
  `reachTimerStart`/`reachTimerFrozenElapsed` は元の「回復」条件のみで判定し、この
  フラグの影響を受けない（リンク変更で反応しないという ADR-0012 の設計を維持する）。
- **却下案 A**: リンク変更のたびに `lastConfirmedStatus` を強制的に `.checking`（未確定）
  に戻す — 却下理由: `lastConfirmedStatus` はポップオーバーの `reachTimerStart` の
  エッジ判定にも共用されているため、これを書き換えるとポップオーバーの経過時間まで
  リンク変更のたびにリセットされてしまい、「ポップオーバーはリンク変更に反応しない」
  という ADR-0012 の意図的な設計を壊す。
- **却下案 B**: リンク変更時に `reachability.checkNow()` を呼んで即座に再チェックを
  強制する — 却下理由: 到達性チェックのタイミングを歪める副作用があり、単に
  「次の（自然な）チェック結果を、メニューバー視点では新規リンクでの初回確認として
  扱う」フラグ方式の方が既存のポーリング間隔（`MonitorConfig.checkInterval`）を
  尊重できてシンプル。

## 決定

`AppState` に `private var menuBarAwaitingFreshReachability = false` を追加する。
リンクエッジ（`linkMonitor.onUpdate` 内、`interfaceType` 変化検知時）で
`freezeMenuBarTimer()` と同時にこのフラグを `true` にする。`apply(results:status:)` の
判定を、ポップオーバー用（`reachTimerStart`/`reachTimerFrozenElapsed`、
`recoveredFromUnreachable`/`justLostReachability` のみで判定）と、メニューバー用
（`resetMenuBarTimer()`/`freezeMenuBarTimer()`、`recoveredFromUnreachable ||
menuBarAwaitingFreshReachability` でリセット判定）とで明確に分離する。

```swift
if status == .reachable && (recoveredFromUnreachable || menuBarAwaitingFreshReachability) {
    resetMenuBarTimer()
    menuBarAwaitingFreshReachability = false
} else if justLostReachability {
    freezeMenuBarTimer()
}
```

## 結果

### 利点

- リンクが変わった後、到達性が既に継続していた場合でも、次の到達確認チェック
  （最大で `MonitorConfig.checkInterval` 秒後）で正しく 0:00 からリセットされ、
  メニューバーのタイマーが凍結されたまま止まり続けることがなくなった。
- ポップオーバーの「到達確認からの経過時間」はこれまで通りリンク変更の影響を受けない。
- 状態遷移シミュレーションで、健全な接続が長時間続いた後にリンクが変わり、次の到達確認で
  メニューバーだけが正しく 0:00 にリセットされ、ポップオーバー側は中断されないことを確認済み。

### 欠点・トレードオフ

- `AppState` の到達性判定ロジックにもう1つの状態（`menuBarAwaitingFreshReachability`）が
  加わり、「メニューバー用」と「ポップオーバー用」で判定条件が非対称になった
  （CLAUDE.md の Elapsed-time semantics に明記して緩和している）。
- リンク変更直後、実際に到達性が確認されるまでのタイムラグ（最大で
  `MonitorConfig.checkInterval`、既定10秒）の間はメニューバーが凍結表示のままになる
  （これは ADR-0014 が意図した挙動であり、本 ADR で変更していない）。
